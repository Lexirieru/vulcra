# E2E evidence — Vault Guardian × FCC Coston2 indexer (2026-07-22)

End-to-end proof that the Vulcra TEE extension (liquidation keeper + Vault
Guardian) is wired into the Flare Confidential Compute stack on Coston2. Raw
machine-readable results: [`e2e-coston2-2026-07-22.json`](e2e-coston2-2026-07-22.json).

hackathon infrastructure provisioned by the Flare admins; they live ONLY in the

## a. FCC indexer DB — connectivity + chain data

Direct probe from this host to the admin-provisioned Coston2 indexer DB
(host/port from the out-of-repo FCC env; MySQL protocol):

- **TCP reachability:** `nc -vz <indexer-host> 3306` → `succeeded!`
- **Auth:** MySQL login as the hackathon user → OK (server `8.0.44-google`, Cloud SQL)
- **Schema:** tables `blocks`, `logs`, `states`, `transactions`
- **Sync state (`states`):**
  - `first_database_block` = 28,300,000
  - `last_chain_block` = 33,102,467 (2026-07-21 17:59:30 UTC)
  - `last_database_block` = 33,102,467 — **indexer fully caught up**
- **Freshness vs chain:** latest indexed block 33,102,477 vs live RPC
  `eth_blockNumber` = 33,102,480 → **lag ≈ 3 blocks (~5 s). The indexer is live.**
- **Scope:** the DB indexes only the FCC/TEE system contracts (2 addresses,
  4,207 logs, 2,705 txs) — e.g. `0x6a0af07b…` (TeeExtensionRegistry-side logs).
  It carries **zero** Vulcra VaultManager logs, which is correct: the ext-proxy
  uses this DB for the **instruction pipeline**, while vault decisions are
  re-read from the chain **inside the enclave** (KTD5).
- **Caveat:** connections are intermittently refused/timed out (shared,
  connection-capped hackathon DB) — retries succeed. Treat `connection
  refused` as route/limit, not a config bug (see README).
- The real `[db]` block now lives in the gitignored
  `config/proxy/extension_proxy.coston2.docker.toml` (from the `.example`).
- The Flare-hosted Coston2 FCC proxy is up:
  `curl https://tee-proxy-coston2-1.flare.rocks/info` returns live `teeInfo`
  (public key, signing-policy ids).

The full ext-proxy Docker container was **not** run locally: the scaffold's
compose expects a `local/tee-proxy` image built from Flare's private monorepo
context, which is not distributed with `fce-extension-scaffold`. Stage (a) is
proven at the transport layer (the exact DB the proxy reads, with the exact
credentials the proxy would use, reading the exact tables the proxy syncs).

## c. Guardian — private rule, live evaluation, auto-repay path

1. **REGISTER (real ECIES):** the driver encrypted the ABI-encoded rule
   `(owner=0x32906b90…, triggerCRBps=20000, maxRepay18=5 vUSD)` to the TEE key
   with `tee-node`'s own `pkg/utils` ECIES; the extension decrypted it via the
   TEE-node `/decrypt` wire API on the sign port and stored it **only in enclave
   memory**, returning
   `termsCommitment = 0x648019d1…` (`keccak256(abi.encode(owner, trigger, maxRepay))`).
2. **EVALUATE (live chain):** the enclave read the vault's live CR = 16,138 bps.
   Since `MCR (13,000) < 16,138 < trigger (20,000)` — inside the private
   protection window — the guardian decided **shouldRepay = true** with
   `repayAmount18 = 969,877,303,078,029,870` (~0.97 vUSD), the exact
   `debt·(trigger−CR)/trigger` needed to lift CR back to the trigger.
3. **EVALUATE (simulated window):** CR = 15,000, debt = 100 vUSD →
   `shouldRepay = true`, repay capped at `maxRepay18 = 5 vUSD`, and the
   execution leg reported
   `decision-only (execution gated): KEEPER_TEE_ADDRESS not set (needs GUARDIAN_EXECUTOR_ROLE)` —
   the live `delegatedRepay` stays gated until a funded TEE keeper wallet holds
   `GUARDIAN_EXECUTOR_ROLE` on the VaultManagers. Nothing is mocked; no
   transaction was submitted.
